## 三、总体设计

### 3.1 数据流

```
巡检计划（inspection_plans）
        │
        ▼ 每日 00:05 生成任务
inspection_tasks (status='pending', task_date=今天)
        │
        ├── 责任人登录 PC 端 ──▶ 我的任务列表
        │                         │
        │                         ▼ 填报结果
        │                  inspection_records
        │                         │
        │                         ├── result='normal' ──▶ task.status='completed'
        │                         └── result='abnormal' ──▶ 可选创建维修工单（3.7）
        │
        └── 当日 23:59 仍未完成 ──▶ missed_scan() ──▶ status='missed'
                                              └── 漏检计数 + 主管通知（>3 次）
```

### 3.2 周期类型与任务生成规则

| `cycle_type` | 说明 | 生成规则 |
|--------------|------|----------|
| `daily` | 每日 | 每天生成 1 条 |
| `weekly` | 每周 | 每周一生成 |
| `monthly` | 每月 | 每月 1 日生成 |
| `quarterly` | 每季度 | 每季度首月 1 日生成 |
| `yearly` | 每年 | 每年 1 月 1 日生成 |

- 计划可设置 `start_date` / `end_date`，超出范围不生成。
- `is_enabled=false` 时不生成。
- 同一计划同一天只生成一条任务（`unique (plan_id, task_date)`）。

### 3.3 任务与设备关系

- 计划按 `org_id` + `device_type_id` 圈定设备范围。
- 生成任务时，将当前范围内所有未退役（`status != 'retired'`）设备作为该任务的待巡检项。
- 填报时逐设备创建 `inspection_records`；全部设备填报完成后 `task.status='completed'`。
- 允许分多次填报：部分填报后 `task.status='doing'`。

### 3.4 漏检判定

- 每日 00:10 扫描昨日 `task_date` 且 `status` 仍为 `pending`/`doing` 的任务，标记为 `missed`。
- 按 `responsible_user_id` 统计近 30 天漏检次数，>3 次时给主管发送系统内通知。

### 4.4 模型骨架

```python
# app/models/inspection.py
class InspectionPlan(Base):
    __tablename__ = "inspection_plans"
    org_id: Mapped[int] = mapped_column(ForeignKey("organizations.id"), index=True)
    device_type_id: Mapped[Optional[int]] = mapped_column(ForeignKey("device_types.id"), index=True)
    cycle_type: Mapped[str] = mapped_column(String(20))
    cycle_days: Mapped[Optional[int]] = mapped_column(Integer, nullable=True)
    responsible_user_id: Mapped[int] = mapped_column(ForeignKey("users.id"), index=True)
    start_date: Mapped[Optional[date]] = mapped_column(Date, nullable=True)
    end_date: Mapped[Optional[date]] = mapped_column(Date, nullable=True)
    is_enabled: Mapped[bool] = mapped_column(default=True)

class InspectionTask(Base):
    __tablename__ = "inspection_tasks"
    plan_id: Mapped[int] = mapped_column(ForeignKey("inspection_plans.id"), index=True)
    task_date: Mapped[date] = mapped_column(Date, nullable=False)
    responsible_user_id: Mapped[int] = mapped_column(ForeignKey("users.id"), index=True)
    status: Mapped[str] = mapped_column(String(20), default="pending")
    completed_at: Mapped[Optional[datetime]] = mapped_column(DateTime(timezone=True), nullable=True)

class InspectionRecord(Base):
    __tablename__ = "inspection_records"
    task_id: Mapped[int] = mapped_column(ForeignKey("inspection_tasks.id"), index=True)
    device_id: Mapped[int] = mapped_column(ForeignKey("devices.id"), index=True)
    result: Mapped[str] = mapped_column(String(20))
    abnormal_desc: Mapped[Optional[str]] = mapped_column(Text, nullable=True)
    photos: Mapped[list[dict]] = mapped_column(JSONB, default=list)
    inspected_by: Mapped[int] = mapped_column(ForeignKey("users.id"))
```

### 后端技术要点

1. **任务生成幂等**：`unique (plan_id, task_date)` 约束 + `INSERT ... ON CONFLICT DO NOTHING`。
2. **周期解析**：使用 `dateutil.rrule` 或手写规则；首版只支持 5 种固定周期。
3. **任务设备清单**：生成任务时不预插设备清单，而是通过计划范围动态查询；填报时逐条创建记录。
4. **任务状态流转**：首次填报 → `doing`；全部设备都有记录 → `completed`；也可手动标记完成。
5. **数据权限**：计划/任务按 `org_id` 过滤；维保人员默认只看责任人为自己的任务（可在前端加筛选）。

## 十五、实现偏离（交付后回填）

> 本节由交付会话补写，记录实际实现与本计划不一致之处。

### D-1（2026-09-13 补记）：B-2/B-3 调度器此前从未接入 lifespan

**计划**：B-2「每日任务生成 | lifespan asyncio 后台任务；按周期规则生成当日任务」，
B-3「每日 00:10 扫描昨日未完成任务并标记 missed」。

**实际**：`app/services/inspection_scheduler.py` 里的 `InspectionScheduler` 写好之后
**从未被任何地方引用**（`git log -S InspectionScheduler -- app/main.py` 为空），
`_periodic_task_generator` 的主循环里留的是 `# ... 具体生成逻辑待补充`。后果是两件事同时不成立：

- FR-033「每日凌晨自动生成当日巡检任务」——所有任务只能靠人工点「生成任务」
- FR-035 漏检扫描——`scan_missed_tasks()` 实现是完整的，但从未被调用过

**已修（2026-09-13）**：按 `app/tasks/offline_monitor.py` 的结构重写调度器并接进
`main.py` lifespan；新增 `INSPECTION_SCHEDULER_ENABLED` /
`INSPECTION_GENERATE_TIME` / `INSPECTION_MISSED_SCAN_INTERVAL_SECONDS` 配置。

### D-2（2026-09-13 补记）：自动生成未按周期规则，且时区口径错误

- **周期规则**：§3.2 规定 weekly→每周一、monthly→每月1日、quarterly→每季度首月1日、
  yearly→每年1月1日。自动生成初版**完全不看 `cycle_type`**，weekly 计划会被每天建一条
  任务（7 倍）。已补 `is_cycle_due()`，并在测试中钉死。
  注：手工 `/generate` 仍按 `get_next_dates_by_cycle()` 从 start_date 步进 N 个日期
  （用户自选跨度），与自动路径的口径差异是刻意的。
- **时区**：PRD OQ-1 明确「默认 UTC+8 00:05」，而后端容器跑在 UTC。按容器本地时间
  会在北京 08:05 才触发，且 `date.today()` 会产出错误日期。已新增 `APP_TIMEZONE` +
  `app/core/timezone.py`，调度器显式按业务时区算 `target_date` 并传给 service；
  **不改容器 TZ**（避免存量 naive 时间戳语义漂移）。

### D-3（2026-09-13 补记）：`(plan_id, task_date)` 唯一约束此前并不存在

§3.2 与本文件第 358 行都以「unique (plan_id, task_date)」作为多 worker 去重的兜底，
`models/inspection.py` 的注释也这么写——但模型没有 `__table_args__`，迁移里也只有外键。
去重完全依赖 `generate_tasks_for_plan()` 的 check-then-act，`WORKERS>1` 下必然双写。
已补 `uq_inspection_tasks_plan_date` 唯一约束 + 迁移，并让 service 捕获 `IntegrityError`
（**仅识别唯一违例**，FK 违例仍上抛，否则任务会静默不生成）。

### D-4（2026-09-13 补记）：`INSPECTION_MISSED_SCAN_TIME` 未按字面实现

本文件「风险应对」一节提到用 `INSPECTION_MISSED_SCAN_TIME` 配置漏检扫描时间，
但代码实现的是**间隔秒**语义（`scan_missed_tasks` 按 `before_date` 回溯扫描），
两者不是一回事。已按代码语义暴露为 `INSPECTION_MISSED_SCAN_INTERVAL_SECONDS`，
未引入一个语义不符的「时刻」配置。
