## 三、总体设计

### 3.1 数据流

```
设备模拟器 / MQTT 适配层（预留）
        │  POST /api/v1/monitor/report   （DEBUG / ALLOW_DEVICE_REPORT 才开放）
        ▼
services/device_report_service.handle_device_report()
        │  同一事务内：
        │   1. devices.status 更新 + devices.last_report_at = now()
        │   2. device_status_logs 写入（复用 3.2 模型）
        │   3. 报警生成/收敛 → alarms（含 org_id 快照、is_drill=false）
        ▼
     Redis Stream  XADD  ws:devices:stream   （MAXLEN ~ 100000）
        │  entry id 即前端 last_msg_id
        ▼
services/ws_broadcaster（每进程一个消费者：XGROUP ws-fanout / $ 起步）
        ▼
ws.ConnectionManager.broadcast(user_scope_filter, frame)
        ▼
前端 MonitorSocket → stores/monitor.js → Dashboard / Map / Notifier
```

**为什么用消费者组而不是逐连接读 Stream：** Stream 提供持久化与补发能力（PRD 2.2），但同一条消息必须送达**每个进程**（多 worker 水平扩展，PRD 7）与**每个连接**（其权限范围内）。因此每进程以独立 consumer name（`{pid}-{uuid}`）加入同一 group，读到全量消息后在进程内扇出给本地连接，满足 PRD 9「Redis Pub/Sub 做多实例广播」的等价语义（Stream 版本，且天然可补发）。

### 3.2 帧协议（PRD 未定义，本计划补充）

服务端 → 客户端：

```json
{
  "id": "1725864000000-0",
  "type": "alarm_new",
  "ts": "2026-09-09T10:30:00+08:00",
  "data": { "alarm_id": 88, "device_id": 12, "device_code": "DEV-SMK-001",
            "device_name": "1F大厅烟感A01", "org_id": 5, "org_name": "1F大厅",
            "alarm_type": "fire", "alarm_level": "critical", "status": "pending",
            "location_description": "1F大厅东侧", "map_x": 120.5, "map_y": 340.2,
            "created_at": "2026-09-09T10:30:00+08:00", "is_drill": false }
}
```

| `type` | 触发点 | 前端动作 |
|--------|--------|----------|
| `alarm_new` | 报警入库 | 列表置顶 + 呼吸灯/滑入 + Notification + 分级提示音 + 地图点位变色 |
| `device_status` | 设备状态变化 | 统计卡片刷新 + 地图点位着色 + 设备详情状态 |
| `alarm_silenced` | 任一端消音（FR-016.1） | 该条停止单条闪烁，状态徽标不变 |
| `alarm_reset` | 复位完成（FR-016.2） | 移除火警/故障标识，点位回 `normal` 色 |
| `pong` / `metrics` | 心跳应答 | 连接质量徽标 |

客户端 → 服务端（仅控制帧，无业务写入）：

```json
{ "action": "ping" }
{ "action": "subscribe", "org_id": 5, "bbox": [0,0,800,600], "last_msg_id": "1725863000000-0" }
```

心跳：服务端每 30 秒（PRD FR-013）主动发送 `{"type":"pong"}`；连续 2 次写失败即摘除连接。

### 3.3 连接认证（补充 PRD 缺口）

浏览器 `WebSocket` 无法自定义请求头，Access Token 直接放 query 会进 Nginx access_log。方案：

1. `POST /api/v1/monitor/ws-ticket`（需 `monitor:view`）→ 返回 `{ ticket, expires_in: 60 }`，Redis 键 `ws_ticket:{ticket}` = `user_id`，一次性使用（握手后立即删除）。
2. 握手 `ws://host/ws/devices?ticket=xxx`，服务端校验失败即 `close(code=4401)`。
3. 前端在 Ticket 过期前重新换取以支持重连。

### 3.4 实时推送的数据权限（关键设计）

`apply_data_scope`（`app/services/user_service.py:31`）按 `model.org_id`（dept）或 `model.created_by`（self）过滤。自动上报的报警 `created_by` 为空，若照搬将导致：`self` 用户收不到任何报警（与 FR-013/014 直接矛盾）；`dept` 用户因 `alarms` 无 `org_id` 而走到 `return query`（**不过滤 = 全量越权**）。

因此：**`alarms` 冗余 `org_id`（写入时从 `devices.org_id` 快照）**，连接建立时解析并缓存该用户的可见 `org_id` 集合，推送前按 `alarm.org_id ∈ scope` 过滤；`data_scope='all'` 全量。self 范围在本模块按"本人创建 + 本人负责区域内设备"处理，需产品确认（13 节 OQ-1）。

### 4.3 模型骨架

```python
# app/models/alarm.py
class Alarm(Base):
    __tablename__ = "alarms"
    device_id: Mapped[int] = mapped_column(ForeignKey("devices.id"), nullable=False, index=True)
    org_id: Mapped[Optional[int]] = mapped_column(ForeignKey("organizations.id"), index=True)
    alarm_type: Mapped[str] = mapped_column(String(20), nullable=False)
    status: Mapped[str] = mapped_column(String(20), default="pending", nullable=False)
    is_drill: Mapped[bool] = mapped_column(default=False, nullable=False)
    device: Mapped["Device"] = relationship("Device")
```

> **不建 `Alarm → Device` 的 `cascade="all, delete-orphan"`**：PRD 3.2 明确要求设备退役/删除时关联报警历史必须保留，`Device.status_logs` 已有 delete-orphan，`alarms` 反向关系必须只读，否则会级联删除报警。

**平面图继承规则：** FR-015 要求上传"**楼层**平面图"（`org_type='floor'`），而 3.2 中 `devices.org_id` 指向**区域叶子节点**（`org_type='zone'`）。两者层级不同，直接用 `device.org_id` 查 `map_image_url` 必然取不到图。规则约定：平面图只挂在 floor 节点；`GET /monitor/map` 与 `GET /monitor/map/devices` 均接受 `org_id` 参数，服务端按「该节点及其祖先中最近持有平面图者」解析目标楼层（CTE 向上递归），并把查询范围扩展为该楼层下的**全部后代区域**设备。前端 `org_id` 语义为"定位到该楼层"，而非"只取该节点直属设备"。

### 5.5 复位（FR-016.2）判定规则

1. 请求体 `{ "physical_restored": true, "remark": "..." }`；`physical_restored` 非 true 直接 400。
2. 若该设备在 `offline_threshold` 内有上报（`last_report_at` 新鲜）：要求最近上报状态为 `normal`，否则 400「设备物理状态未恢复，禁止复位」。
3. 若无上报通道（模拟器/未接入 MQTT）：`physical_restored=true` + 强制写审计留痕（`reset_by` + `remark`），允许复位。
4. 效果：`alarms.status='resolved'` + `resolved_at`；`devices.status='normal'` + `device_status_logs`（`reason='系统复位'`）；广播 `alarm_reset`。
5. `retired` / `shield` 设备禁止复位（屏蔽需走解除屏蔽，属 3.2/后续）。

### 5.6 历史轨迹（FR-018）

| 方法 | 路径 | 描述 | 权限 |
|------|------|------|------|
| GET | `/api/v1/devices/{id}/trajectory` | **本计划新增**：`start`/`end`（默认近 7 天，最长 90 天）+ 分页，仅返回 `device_status_logs` 同构时间序列，供折线/甘特展示 | `device:view` |
| GET | `/api/v1/devices/{id}/trajectory/export` | `format=xlsx|csv`，≤1 万行同步导出（>1 万行走 3.9 异步任务，本计划先限制并提示） | `device:view` |

与 3.2 `GET /api/v1/devices/{id}/history` 的区别：history 是**跨类别聚合**（状态+报警+维修+巡检），trajectory 是**单类别时序 + 时间区间 + 可导出**。两者共用 `device_history_service`，避免重复实现。

### 后端技术要点

1. **上报事务边界**：`devices` 更新 + `device_status_logs` + `alarms` 插入在同一 `async_session.begin()` 内；`XADD` 放在 commit **之后**（避免回滚却已推送）。推送失败仅记 warning，不回滚业务。
2. **报警去重**：同一 `device_id` 存在未收敛（`status NOT IN ('resolved','false_alarm')`）同类报警时更新而非新建，防风暴（模拟器 1s 上报一次即触发）。用 4.1 的 partial index 保证查询代价。
3. **Stream 与补发**：`XADD ws:devices:stream * data <json>`；补发用 `XRANGE key (last_msg_id +`。消费者名 `{hostname}-{pid}-{uuid}`，启动时 `XGROUP CREATE ... MKSTREAM` 幂等捕获 `BUSYGROUP`。
4. **多 worker**：开发 `--reload` 单进程；生产每 worker 各持一个消费者，水平扩展无需共享内存连接表（PRD 7 无状态设计）。
5. **WS 权限快照**：连接时计算可见 `org_id` 集合并缓存于连接对象；区域结构调整后需重连生效（记录为已知限制）。
6. **静态资源安全**：`/static/maps` 仅允许匿名读 PNG（平面图不含敏感数据）；若后续接 MinIO 改为预签名 URL（PRD 6.2）。
7. **`apply_data_scope` 复用限制**：该函数依赖 `query.column_descriptions[0]["entity"]`，仅适用 `select(Model)` 形态；`dashboard` 的聚合查询（`select(func.count())`）不适用，须在 service 层手写 `org_id IN (...)`，勿误用。

### 10.4 联调与性能

1. **延迟基准**：模拟器固定 100 条/s，`report_ts` 与前端 `onmessage` 时间差 P95 ≤ 2s、P99 ≤ 3s。
