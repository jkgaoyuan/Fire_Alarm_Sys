## 三、总体设计

### 3.1 数据流

```
业务表（devices/alarms/inspection_tasks/repair_orders）
        │
        ├── 聚合 API ──▶ 统计看板（ECharts）
        │
        ├── 导出任务 ──▶ BackgroundTasks 流式写 Excel
        │                    │
        │                    ▼ 完成
        │              report_export_tasks.status='completed'
        │                    │
        │                    ▼ WS 推送 / 轮询下载
        │              前端通知用户下载
        │
        └── 写操作中间件 ──▶ audit_logs
```

### 3.2 统计口径

| 看板 | 口径 | 默认过滤 |
|------|------|----------|
| 设备完好率 | 按 `devices.status` 分组计数 | `is_deleted=false`、`status != 'retired'`、`is_drill=false |
| 报警趋势 | 按 `alarms.created_at` 日期 + `alarm_type` 分组 | `is_drill=false` |
| 故障 TOP10 | 按 `repair_orders.device_id` 计数，取前 10 | `status='completed'`、`source != 'drill'` |
| 巡检完成率 | `completed / (completed + missed)` 按责任人/区域 | 时间范围可配 |

### 3.3 区域下钻

- 设备完好率饼图支持点击某个区域进入该区域的下级视图。
- 后端按 `organizations` 树递归计算各节点汇总；前端使用面包屑导航。

### 3.4 异步导出流程

1. 用户点击导出 → 后端创建 `report_export_tasks` 记录，返回 `task_id`。
2. `BackgroundTasks` 启动流式查询并写入 `.xlsx`/`.csv`。
3. 前端轮询 `GET /reports/export/{task_id}/status` 或等待 WS `report_export_completed`。
4. 完成后下载 `GET /reports/export/{task_id}/download`。
5. 文件保存于本地卷或 MinIO（首版本地卷）。

### 3.5 操作审计范围

- 审计所有 `POST/PUT/DELETE/PATCH` 写接口（除登录/刷新等认证接口）。
- 记录：`user_id`、`username`、`operation`（CREATE/UPDATE/DELETE/LOGIN/LOGOUT）、`module`、`method`、`request_url`、`request_params`、`old_value`、`new_value`、`ip_address`、`user_agent`、`created_at`。
- 通过 FastAPI 中间件或依赖注入实现；`old_value`/`new_value` 由业务层提供（中间件只记录请求参数，完整 diff 由服务层补充）。

### 后端技术要点

1. **统计查询优化**：设备/报警聚合使用 `count(*)` + `GROUP BY`；大数据量用物化视图或缓存（首版直接查询，>3 秒时加缓存）。
2. **区域下钻**：后端按 `organizations` 树计算可见节点；前端传入 `org_id` 时返回该节点及子节点汇总。
3. **异步导出流式写**：使用 `openpyxl` 的 `write_only=True` 模式，分批查询（每次 1000 行），避免内存溢出。
4. **审计 old/new diff**：中间件记录请求参数；业务服务在更新/删除后将 `old_value`/`new_value` 写入同一条审计记录（通过 `audit_service.update_diff`）。
5. **180 天保留**：首版不实现自动清理；3.10 用 lifespan 后台任务清理。

## 十一、风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|----------|
| 统计聚合慢 | 看板加载 >3 秒 | 加复合索引；>3 秒时引入 Redis 缓存或物化视图 |
| 大导出阻塞主线程 | 服务无响应 | 使用 BackgroundTasks + 流式写；单任务限制内存 |

| old/new diff 不完整 | 审计价值低 | 业务层统一封装 update/delete 方法，强制写入 diff |
| Celery 引入压力 | 架构复杂度上升 | 首版用 BackgroundTasks；确有需要时 3.10 统一引入 |
